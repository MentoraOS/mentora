## 1. Executive Summary

**Pourquoi cette phase existait.** Au Foundation Freeze, Mentora était au niveau de maturité CI **zéro — assumé** : toute la preuve du système (la gate 112/112, les contract suites sur PostgreSQL réel, le boot du premier exécutable) vivait sur une seule machine et tenait par la discipline d'une seule personne. La stratégie CI/CD (GitHub Governance, Lot 5) avait écrit la loi ; rien ne l'exécutait. La condition suspensive du GO du Freeze exigeait que la preuve devienne un **fait d'infrastructure** avant tout lot de code R5.

**Ce qu'elle devait accomplir.** Transformer cinq intentions documentées en cinq gardiens exécutables : la gate sur chaque poussée (`ci`), la preuve nocturne de déterminisme (`nightly`), la chaîne de certification de release (`release`), la défense automatique de la Constitution (`docs`), et la gouvernance des dépendances (`supply-chain` + Dependabot) — sans jamais que la CI ne remplace les Foundations : elle les applique.

**Pourquoi elle est terminée.** Les cinq gardiens existent, sont commités, poussés, et prouvés — trois exécutions GitHub vertes consécutives pour la gate, validations réelles ou locales outillées pour chacun des autres (§5). La phase a de surcroît payé ses propres découvertes : deux défauts dormants (corepack/clés npm, baseline Node jamais exercée) trouvés et tués **par le premier contact avec la réalité** — exactement ce pour quoi une phase de smoke existe.

## 4. Décisions d'architecture (le pourquoi de chacune)

1. **CI-identique** — la CI exécute `pnpm verify`, la commande du développeur, jamais recomposée : deux commandes seraient deux vérités.
2. **Check unique `verify`** — la gate est UNE ; la décomposer en checks nommés serait la reconstruire à la main.
3. **Nightly froid + double passe** — le cache PR optimise, la nuit prouve ; deux exécutions réelles qui concordent = déterminisme, un écho de cache ne prouve rien.
4. **Release Candidate / Official** — un seul pipeline, deux canaux par déclencheur ; le tag est l'acte officiel ; l'officiel se grave en GitHub Release permanente.
5. **SBOM indépendant (syft, lockfile)** — l'inventaire d'une release ne peut dépendre ni d'un plan GitHub ni d'un réseau tiers au moment de certifier.
6. **Release Manifest** — une release doit être retrouvable entière depuis UN document, par empreintes.
7. **SHA pinning universel** — actions par SHA de commit, binaires par version + checksum officiel : un tag mobile est une supply-chain ouverte.
8. **Provenance à deux niveaux** — la preuve garantie (documentaire) n'attend pas la preuve idéale (attestation signée, liée au plan) ; le best-effort est DÉCLARÉ, jamais silencieux.
9. **Canon Protection exécutable** — le Titre VII cesse d'être une discipline pour devenir un verrou : label `titre-vii` ou échec.
10. **Dependabot natif, majors ignorés** — zéro accès tiers au dépôt privé ; un major est une décision (ADR), pas une notification.
11. **Outils premier-parti zéro dépendance** — le même outil en local et en CI, sans rien ajouter à la chaîne qu'il audite.
12. **Permissions minimales par job** — `contents:read` partout ; trois élévations au total, chacune portée au seul job qui la consomme (`issues:write`, `id-token`+`attestations:write`, `contents:write`).

## 6. État de la plateforme

Mentora sait désormais : **prouver chaque poussée** (gate complète, base réelle, sur runner neutre — plus jamais « ça marche sur ma machine ») ; **se re-prouver chaque nuit à froid, deux fois** (le non-déterminisme a un détecteur) ; **certifier une release** (artefact + inventaire double format + provenance + manifest par empreintes, canaux candidate/official) ; **défendre sa Constitution automatiquement** (le canon n'est plus modifiable silencieusement par PR) ; **gouverner ses dépendances** (trains hebdomadaires bornés, majors par décision, chaîne d'approvisionnement inventoriée chaque semaine avec une loi bloquante). Le tout avec des permissions minimales, des composants épinglés, et des outils qui tournent à l'identique sur un poste et dans le cloud.

## 9. Leçons apprises

1. **Corepack** : un outil d'amorçage embarque ses clés de confiance — les clés tournent, l'outil s'épingle ; on ne désactive JAMAIS la vérification pour « débloquer ».
2. **Node baseline** : une baseline déclarée mais jamais exercée est une fiction — la CI est son premier test honnête ; tout invariant déclaré doit être exercé par une machine.
3. **GitHub Re-run** : un re-run rejoue le SHA et le workflow d'origine, pour toujours — on ne teste jamais le présent en relançant le passé.
4. **SBOM** : la bonne source d'inventaire est le lockfile commité, pas le disque ; et scanner node_modules noie l'outil.
5. **Lockfile** : `--frozen-lockfile` partout — la CI n'invente pas de résolutions.
6. **Nightly** : un second run sur cache est un écho (9,4 s mesurées) — purger la mémoïsation entre les passes ou ne rien prouver.
7. **Release Manifest** : sans référence unique par empreintes, une release est un tas d'artefacts, pas un objet.
8. **SHA pinning** : les tags des actions sont légers — les épingler PAR COMMIT, résolu depuis la source, jamais de mémoire.
9. **Supply chain** : l'outil qui audite la chaîne ne doit rien lui ajouter (premier-parti, zéro dépendance).
10. **Hygiène d'environnement** (héritée du Freeze, confirmée) : un processus zombie sur une base partagée fabrique des faux rouges — `kill` MSYS ne tue que le wrapper.

## 15. Héritage de la phase

_Cette section est le passage de relais officiel. Elle s'adresse aux développeurs et CTO qui liront ceci dans cinq ans._

**1. Ce que cette phase vous laisse.** Avant elle, la preuve de Mentora était un rituel personnel ; après elle, c'est une infrastructure. Vous héritez de cinq gardiens qui tournent sans qu'on le leur demande : chaque poussée est vérifiée par la gate intégrale sur base réelle ; chaque nuit, la plateforme se reconstruit deux fois à froid et compare ; chaque release est un objet certifié retrouvable par empreintes ; chaque tentative de toucher la Constitution par PR échoue sans la marque du Titre VII ; chaque lundi, la chaîne d'approvisionnement est inventoriée et toute action non épinglée fait échouer le rapport. Vous n'avez pas à faire confiance aux auteurs de cette phase : relisez les runs.

**2. Les décisions devenues invariants.** CI-identique (la CI exécute la commande du développeur, à la lettre) · Nightly Cold Gate (le déterminisme se prouve deux fois, à froid) · Candidate avant Official (le tag est l'acte, la candidate est la répétition) · SBOM à chaque release, depuis le lockfile · Release Manifest comme référence unique par empreintes · SHA pinning universel (actions par commit, binaires par checksum) · Canon Protection exécutable · Dependabot gouverné, majors par ADR · outils d'audit premier-parti zéro dépendance · permissions minimales par job.

**3. Ce qui ne se rediscute plus sans ADR ou Titre VII.** Recomposer `verify` à la main ; exiger un check qui n'existe pas ; désactiver une vérification de signature « pour débloquer » ; dépingler une action ou un binaire ; introduire un outil tiers dans la chaîne d'audit ; merger un major sans ADR ; toucher `docs/canon/` hors procédure ; élever une permission de workflow hors du job qui la consomme. Chacun de ces gestes défait une loi de cette phase — il exige le niveau de décision qui l'a créée.

**4. Les enseignements qui doivent guider toutes les phases futures.** Tout invariant déclaré doit être exercé par une machine (la baseline Node a dormi fausse pendant toute une génération de lots parce qu'aucune machine ne la lisait). Le premier contact avec la réalité vaut plus que dix validations sur environnement complaisant — provoquez-le tôt. Un re-run rejoue le passé. Les échecs de CI sont des données : chacun des deux rouges de cette phase a payé sa dette en léguant une loi.

**5. Les lois techniques permanentes.** _La CI applique les Foundations ; elle ne les remplace jamais._ _La preuve ne se recycle pas._ _Une release n'invente rien : elle certifie, documente, prouve._ _Une dépendance n'est jamais mise à jour parce qu'elle est plus récente : elle est mise à jour parce qu'elle est gouvernée._ _Le Canon est une loi, et une loi se défend toute seule._ Si un jour l'une de ces phrases devient fausse dans le dépôt, ce n'est pas la phrase qu'il faut corriger.
